## 2. 審査メモ（App Review Information の Notes 欄にそのまま貼る）— v1.1.0

```
本アプリは v1.0 から内容を全面的に変更し、「部屋の防音性の診断」に特化したアプリになりました
(v1.0 は Guideline 4.3(a) のご指摘を受け、コンセプトを見直しました)。

【アプリの目的・独自性】
一般的な騒音計(dBメーター)とは異なり、以下を独自実装しています。
1. 内見診断: 部屋の中央/窓際/隣室側の計測に加え、壁のノック音のスペクトル重心と減衰時間、
   手叩きの残響時間(RT60換算)を解析し、窓・壁・ドアの弱点と壁の重さを推定して防音スコアを算出
2. 音の侵入マップ: ARKit のワールドトラッキングで端末位置を追跡しながらレベルを記録し、
   空間上にヒートマップとして表示
3. 対策シミュレーター: オクターブバンド別の減衰量テーブルを用いて、対策ごとの予測ΔdBと費用を算出
4. 対策の Before/After 検証
すべてオンデバイスで完結し、テンプレートや購入したコードは使用していません。

【アカウント不要】
ログイン機能はありません。起動してすぐ全機能をお試しいただけます。

【アプリ内課金・広告】
ありません。すべての機能を無料でご利用いただけます。

【カメラの使用について】
ARマップで端末の位置を追跡するためだけに使用します。映像は保存・送信しません。
ARKit のワールドトラッキング非対応端末では、対応していない旨を表示します。

【アカウント不要】
ログイン機能はありません。起動してすぐ全機能をお試しいただけます。

【マイクの使用について・重要】
本アプリはマイクを騒音レベルの計測にのみ使用します。音声データは端末内で
リアルタイムに解析されるだけで、録音として保存されることはなく、外部サーバーへ
送信されることも一切ありません。計測が終わると数値化された結果（dB値・周波数帯
ごとのレベル・検出音のラベル等）のみがアプリ内に保持されます。

【音源推定について】
検出音の種類（車・話し声等）の推定にはApple純正のSoundAnalysisフレームワーク
（SNClassifySoundRequest）を使用しており、これもオンデバイスで完結します。
外部のAIサービスや通信は一切使用していません。

【通信・データ収集について】
Firebase Analytics/Crashlyticsによる匿名の利用状況・クラッシュ計測のみ通信が
発生します。計測結果や音声データそのものが送信されることはありません。

【アプリ内課金・広告】
ありません。すべての機能を無料でご利用いただけます。

【動作確認の手順】
1. 起動 → ホームの「内見診断」→ 物件名を入力して「診断を始める」
2. 5ステップを順に実施(各ステップは「飛ばす」も可)。計測ステップは15秒、
   ノック/手叩きは「待機して叩く」を押してから1回叩く
3. 結果画面: 防音スコア・等級・弱点・壁の推定 → 「効く対策を予測する」で対策シミュレーター
4. ホーム「騒音計」→「計測を開始」→ 結果(周波数帯・時間推移) → 「効く対策を予測する」
5. シミュレーターで「この対策を試す」→ ホーム「対策の効果を検証」に記録され、
   「対策後を計測する」で再計測すると実測ΔdBが出る
6. ホーム「音の侵入マップ」→ 「開始」→ 壁・窓に沿って端末を動かす → 「終了して結果を見る」
```

### 音の大きさの計算の誤り（結果の dB が約83dB大きかった）

- **原因**: `AudioSpectrumAnalyzer` が FFT のパワー（片側ビンの |X|² の和）を、サンプル数・窓の電力で割らずに
  dB にしていた。vDSP の実数 FFT は真の DFT の2倍（|X|² は4倍）、Parseval で片側の和は N²/2·mean(w²)·RMS²、
  hann（`.hanningDenormalized`）の mean(w²)=3/8 なので、正しい係数は 4 × N²/2 × 3/8 = **0.75·N²**
  （N=16384 → 10·log10 = **83.04dB**）。結果の Leq・帯域・ピーク・最小・時系列が、RMS 経路
  （`InstantLevelMeter`・`ImpulseAnalyzer`、2026-08-29 に騒音計でオフセット100を合わせた経路）より約83dB大きかった。
  その値が結果画面・3段階判定（40/60dB）・室内の静けさ (Leq−40)×1.5・対策シミュレーター・Before/After・校正に
  そのまま使われていた（室内の静けさはほぼ常に上限の30点減点、校正は −20dB で止まる）
- **直し方**: `dbFromPower` で `fftPowerScale = 0.75·N²` で割る（`AudioSpectrumAnalyzer.swift`）。計測中の表示は
  同じ関数を通る直近の FFT 窓の値なので、表示と結果は同じ物差しのまま
- **保存済みの記録**: 1.1.1 までの内見診断（中央・窓際・隣室側）と対策の記録（Before/After）の絶対値の dB
  （全体の Leq・ピーク・最小、帯域、時系列）を、読み込むときに1回だけ「−83.04dB − 当時の校正値」ずらす
  （`LevelScale`、`InspectionRepository.legacyShiftDb`）。1.1.1 の記録には当時の校正値
  （`calibration_adjustment_db_v1`、多くは −20dB）が足されているので、それを取り除いて校正 ±0 の新しい物差しに
  そろえる（−20dB なら −63.04dB、校正していなかった人・新規は −83.04dB）。版の印が無かったので、保存キーを
  `inspections_v1` → `_v2`、`countermeasure_records_v1` → `_v2` にしたことを印にした（`_v2` を書いてから `_v1` を
  消す。`_v2` があれば換算しない）。`_v1` が壊れていて読めないときは `_v2` を書かず `_v1` も消さない（端末に残す。
  以前は `[]` を書いて消していた）。ノック・手叩き（`ImpulseAnalyzer`、RMS 経路）と予測ΔdB は変えない。
  窓際・隣室側の差・Before/After の差は両方が同じだけずれるので変わらない。騒音計の結果・AR マップは保存していない。
  PDF は読み込んだ記録から作るので換算後の値
- **校正**: 1.1.1 の校正値（ref − 古い Leq）は意味が無いので、1回だけ 0 にし（`calibration_adjustment_db_v2` に
  保存）、0 以外だったときは校正画面に「音の大きさの計算を直したため…校正を初期値(±0dB)に戻しました」を一度だけ
  出す。記録の換算が古い校正値を読むので、`_v1` は校正のリセットと記録の換算の両方が終わってから消す
  （`CalibrationRepository.removeLegacyIfMigrated`。どちらの読み込みが先でも同じ結果。読めない古い記録が残っている
  間は `_v1` も残す）
- **検証（macOS で同じ Swift に合成信号、48kHz、A特性ゲインを1にした写しも並べた）**:

  | 入力 | RMS 経路 | A特性なしの Leq | 結果の Leq（A特性） | 計測中の表示 |
  |---|---|---|---|---|
  | 1kHz 正弦波 振幅0.01 | 56.99 | 56.99（差0.00） | 56.99 | 56.99 |
  | 100Hz 正弦波 振幅0.01 | 56.99 | 56.99 | 37.85（−19.1、A特性ぶん） | 37.85 |
  | 4kHz 正弦波 振幅0.01 | 56.99 | 56.99 | 57.95（+1.0） | 57.95 |
  | 1kHz 振幅0.0001 / 0.3 | 16.99 / 86.53 | 一致 | 16.99 / 86.53 | 一致 |
  | 白色雑音 ±0.01 | 55.22 | 54.97（−0.25、帯域外 <22Hz・>22.6kHz） | 52.47 | 52.33〜52.61（平均52.47） |

  直す前は同じ 1kHz・振幅0.01 で結果 140dB だった。白色雑音 ±0.001 でも同じ差（−0.25 / −2.74）。
  静かな音の大きさの入力で 100dB を超えない

**提出前に実機で確かめること**: 静かな部屋で計測中の表示と結果が近い値で、100dB を大きく超えないこと
（合成信号では確かめたが、実機のマイクの値はまだ見ていない）。以前の版で保存した診断が、更新後に 83dB ほど（−20dB に校正していた端末では 63dB ほど）下がった値で開け、窓際・隣室側の評価が
変わらないこと。以前に校正していた端末で、校正が ±0dB に戻り、校正画面に案内が一度だけ出ること。
手持ちの騒音計があれば、校正値が ±20dB の範囲に収まること。
