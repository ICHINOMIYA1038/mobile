# 宅建 AI チューター（仮称: 宅建トーク）— 企画・設計（2026-09-24）

## 1. コンセプト

**「AI とずっと話し続けていたら、合格まで導かれる」。**
学習者はアプリを開いて AI と会話するだけ。何を勉強するか、どの順番か、いつ復習するかは AI が決める。
pairof.jp の「教材（ゴールと採点基準）× 学習者の状態を見ている AI 相棒 × 提出→評価のループ」を、
宅建（2027年10月試験）に載せ替える。

既存の `apps/takken_simple`（300問・解説・根拠条文・用語集50語・配点比率・間隔反復）を**教材と記録の土台**として流用する。

## 3. 学習シナリオ（会話の設計）

### 3.1 一日の流れ

1. **開始**: AI が「今日は権利関係の『意思表示』から。まず3分で要点を説明するね」と切り出す（学習者は何も決めなくてよい）
2. **講義**: 論点を対話で説明。途中で「ここまでで、詐欺と強迫の違いを一言で言うと？」と**学習者に言わせる**（能動想起）
3. **確認問題**: `takken_simple` の一問一答を AI が出題（ツール呼び出し）。○×→即解説→間違えたら別の角度でもう一問
4. **記録**: 正誤・理解度・所要時間を保存。次回の復習日を決める（間隔反復のスケジューラは既存を流用）
5. **締め**: 「今日はここまで。明日は『代理』。合格グラフは 12.4→13.1 点」と進捗を数字で見せる

### 3.2 カリキュラム

`takken_simple` の分野（宅建業法／権利関係／法令上の制限／税その他）と中区分（11区分）を**章**とする。
章ごとに「講義の要点（AI に渡す教材 Markdown）」「確認問題（既存300問から割当）」「合格基準（正答率・説明できるか）」を持つ。
pairof のレッスン Markdown（goal / rubric / slides）と同じ構造にする。

- **第1章「宅建業法：免許・宅建士・保証制度」を無料**にする（最も配点が高く、学習者が最初にやる章。ここで体験を作る）
- 2章以降は課金

### 3.3 AI の振る舞い（システムプロンプトの要点）

- 学習者の現在地（章・正答率・苦手論点・直近の会話要約）を毎回コンテキストに入れる
- 説教しない。求められたら答えを出す。ただし「答えを見る前に一度考えてもらう」は保つ
- 法令の正確性: 教材にある根拠条文の範囲で答え、教材外は「教材の範囲外なので断定しない」と言う（ハルシネーション対策）
- 出力は短く（スマホで読む）。1回の返答は 300 字以内を基本に、講義は複数ターンに分ける

### 3.4 AI のツール（tool use）

| ツール | 役割 |
| --- | --- |
| `get_next_question(chapter, exclude)` | 既存問題集から出題 |
| `record_answer(question_id, correct, note)` | 記録＋間隔反復の更新 |
| `get_progress()` | 合格グラフ・章ごとの到達度 |
| `set_plan(next_chapter, review_ids)` | 次回の予定 |
| `lookup_term(name)` | 用語集（50語） |

## 4. アーキテクチャ

```
iOS (Flutter)  ──HTTPS──▶  Backend (Cloudflare Workers + D1)  ──▶  Claude API
   │                          │  ・ユーザー＝匿名ID（Sign in with Apple は任意）
   │  StoreKit (RevenueCat)   │  ・トークン残高・章の解放状態
   └──────────────────────────┤  ・会話履歴（要約＋直近N件）・学習記録
                              │  ・システムプロンプト＋教材＋ツール定義
                              └─ RevenueCat Webhook で残高付与
```

- **Backend は pairof と同じ Cloudflare Workers + D1**（実績あり・無料枠で始められる・pairof のクレジット管理コードを流用できる）。gikyoku（Next.js/Vercel）は関係ないサービスなので混ぜない
- **Claude 呼び出しはすべてサーバー経由**（鍵をアプリに置かない）。会話は Messages API、教材・ツール定義・システムプロンプトを `cache_control` でキャッシュして入力コストを下げる
- **モデル**: 既定は `claude-opus-5`（Anthropic の推奨既定）。コスト検証の結果で `claude-sonnet-5` に落とす判断はユーザーがする。効果検証は `effort: low〜medium` で十分（会話用途）
- **会話の長期化**: 履歴は「章ごとの要約＋直近 20 ターン」に圧縮してサーバーで保持（1M コンテキストに頼らない。コストのため）

## 5. 費用と価格

### 5.1 1ターンの原価（概算）

| 項目 | トークン | 単価 | 円換算(¥150/$) |
| --- | --- | --- | --- |
| 入力（システム＋教材＋履歴、キャッシュ命中） | 6,000 | Opus 5: $5/M（キャッシュ読込は約1/10） | 約 ¥0.5〜4.5 |
| 出力（300字≒400トークン） | 400 | Opus 5: $25/M | 約 ¥1.5 |
| **1ターン合計** | | | **約 ¥2〜6（Opus 5）／ ¥1〜2.5（Sonnet 5）** |

1セッション 20 ターン ≒ ¥40〜120（Opus）。毎日使う人で月 ¥1,200〜3,600。
**したがってサブスクは ¥980/月 では Opus だと赤字になりうる。** 選択肢:

- (a) **トークン制（買い切り消費型）**: 「10,000 トークン ¥600」「50,000 トークン ¥2,400」のようなパック。原価が価格に連動するので安全。pairof の `credit_usage` と同じ考え方
- (b) **サブスク＋月間上限**: ¥1,480/月で月 300 ターンまで、超過はパック購入。継続収入になるが上限設計が要る
- (c) 併用: 無料の第1章（例: 60 ターンぶん）→ サブスク基本＋パック

**推奨は (c)**。App Store 手数料 15%（小規模事業者）込みで、月 ¥10,000 の目標は継続 10 人前後で達成できる。

### 5.2 無料枠の上限

第1章は無料だが、AI 費用がかかるので**無料枠にもターン上限（例 60 ターン）**を置く。上限後は「続きは Pro で」。

## 6. App Store 審査で押さえること

- AI 生成コンテンツ: 「AI の回答は誤りを含むことがある。法令の原文で確認を」を初回と設定に明記（takken_simple の免責と同じ）
- 年齢制限 4+ のまま（宅建の内容は無害）。ただし「制限のない Web アクセス」には該当しない
- 課金は StoreKit 必須（RevenueCat）。トークン残高は「消費型 IAP」。復元ボタン
- プライバシー: 会話内容をサーバーに保存する旨（匿名ID・学習目的・第三者提供なし）。App Privacy は「ユーザーコンテンツ（その他）」「識別子」を収集・紐付けなし
- 4.3(a)（類似アプリ）対策: 説明文・スクショで「AI が主導する合格カリキュラム」を前面に。問題集アプリの見た目にしない（会話画面が主役）

## 7. MVP の範囲（4〜6週間）

1. Backend: Workers + D1、匿名ユーザー、Claude プロキシ（ストリーミング）、ツール5つ、トークン計測、RevenueCat Webhook
2. 教材: 第1章＋第2章の講義 Markdown（各 6〜8 論点）。問題は既存を割当
3. アプリ: 会話画面（ストリーミング表示・○×ボタンのカード）、進捗（合格グラフ流用）、課金、設定
4. 運用: 費用上限（1日のターン上限・GCP と同じ発想の予算アラート）、会話ログの匿名レビュー
5. ストア: スクショ（会話が主役）、`docs/store-listing.md`、審査メモ

3章以降の教材は公開後に週1章ずつ追加（「教材が増えていく」は継続の理由になる）。
