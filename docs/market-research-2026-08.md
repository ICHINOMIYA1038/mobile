# 次に作るアプリのニーズ調査（2026-08-28）

目標: **月1万円** の収益が見込める iOS アプリの題材を決める。
調査方法は (1) iTunes Search API（JPストアフート）で候補キーワード約100語の競合を実測、
(2) Web上の困りごと・個人開発の収益事例の裏取り。実測スクリプトは末尾に再掲。

## 1. 月1万円の算数 — 広告モデルでは届かない

| モデル | 手取り単価 | 月1万円に必要な数 | 新規個人アプリでの現実性 |
|---|---|---|---|

| サブスク ¥300/月 | 約¥255 | **継続40人** | ○ 「毎月使う理由」がある業務系向き |

既存ポートフォリオ（全アプリ合計で評価1件）が示す通り、広告モデルは母数がないと機能しない。

## 4. 実測で見えた2026年の市場の変化

- **AI支援による個人開発アプリの洪水**: ほぼ全キーワードで「2026-06〜08リリース・評価0件」のアプリが複数並ぶ。空きニッチは数ヶ月で埋まるので、**着手から提出まで1〜2ヶ月**で出す前提が要る。
- **資格アプリは工場化**: 4〜5社が同じテンプレで全資格を網羅しつつある。資格ジャンル全体を候補から外すのが安全。
- **参入者は多いが勝者不在のニッチ**（A1・A2）は、参入者の評価が0〜3件で止まっている＝ストア掲載だけでは見つけてもらえない。教室の先生コミュニティ・競技団体・部活顧問への直接の紹介（SNS/ブログ/知恵袋回答）が初期の数十本を作る現実的な経路。

## 5. 推奨と次のアクション

**第1候補: A1 個人教室の月謝・出欠・振替管理**
- 理由: 困りごとが生の言葉で確認でき、払う人が明確（先生）で、毎月使う業務なのでサブスク（¥300〜480/月）か買い切り（¥1,500〜2,000）どちらでも設計できる。月1万円 = 継続30人強。
- 勝ち筋: 法人SaaS（スクの助・Sgrum）は生徒側アプリ必須で重い。**先生1人・オフライン・入力3タップ**（出席○×→月謝入金→振替残）に絞り、CSVエクスポートと確定申告向け年間集計を付ける。
- MVP範囲: 生徒台帳 / レッスン予定 / 出欠 / 月謝入金・未納 / 振替残数 / 月末サマリー / CSV。連絡機能・予約機能は作らない。

**第2候補: A2 バレーボール or バドミントン専用スコアシート**
- 弓道Pro・Best Bowlingと同じ「無料版 + Pro ¥600」の2段構え。部活の顧問・審判講習向け。
- 着手前に競技人口（日本バレーボール協会 登録約40万、バドミントン協会 約30万）と、大会公式スコアシート形式の再現可否を確認。

**第3候補: A3 アマ無線ログ**は市場が最も小さいが客単価が高い。A1/A2の後の候補として残す。

着手時に必ず通す手順（既存資料）:
1. `scripts/create_app.sh` で作成（`CFBundleDevelopmentRegion=ja_JP` 自動適用）
2. 提出前に `docs/store-listing.md` を書く（`apps/takken_simple/docs/store-listing.md` がテンプレ）
3. スクリーンショットは `docs/screenshot-guidelines.md` の4原則（全枚に見出し・色帯・数字・アイコン配色）
4. 提出は `ios-app-review-submission.md`

## 付録: 競合実測スクリプト

```python
# python3 probe.py "習い事 月謝 管理" "バレーボール スコア" ...
import json,sys,urllib.parse,urllib.request,time
def probe(term):
    u=f"https://itunes.apple.com/search?term={urllib.parse.quote(term)}&country=jp&entity=software&limit=25"
    d=json.load(urllib.request.urlopen(u))["results"]
    strong=[r for r in d if r.get("userRatingCount",0)>=1000]
    paid=[r for r in d if r.get("price",0)>0]
    print(f"### {term}  count={len(d)}  >=1000件:{len(strong)}  有料:{len(paid)}")
    for r in d[:6]:
        print(f"  {r.get('userRatingCount',0):>6}件 {r.get('averageUserRating',0):.1f} ¥{int(r.get('price',0)):>5} {r['trackName'][:40]} | {r.get('sellerName','')[:18]} | {r.get('currentVersionReleaseDate','')[:10]}")
for t in sys.argv[1:]:
    probe(t); time.sleep(0.4)
```

**(a) 画像認識・音声DSP・OMR などクローンに数週間では作れない中核技術がある**、
**(b) 検索結果が10件未満 or 既存が★3以下**、**(c) 払う人が明確**。

**技術の堀の条件**: 外部APIを叩くだけでは堀にならない（将棋局面図Makerが実例）。
**オンデバイスモデル＋ユーザーの修正データで精度が上がる仕組み**が、クローンが追いつけない部分。

推奨は **T1（将棋）**: 認識対象が固定（駒8種×2色、9×9）で精度を出しやすく、失敗しても手修正UIで補える。
農工大の2019年研究で99%超が示されており実現可能性が高い。将来「対局動画→棋譜」に拡張すれば唯一無二。
次点 **T2（楽譜OMR）** は需要が大きいが精度到達の難度が桁違いに高く、童謡・保育曲（単旋律＋簡易伴奏）に絞れば現実的。
